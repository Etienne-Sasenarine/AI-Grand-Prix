# First real smoke-test run: 10 pass, 4 fail

Isaac Sim finally ran on RunPod (see `DEPLOY_PROCEDURE.md`). This is what the
first execution of `scripts/smoke_test.py` against live PhysX found.

## 1. The aircraft weighs five times too much — **critical**

```
BODY_NAMES:    ['body', 'prop1', 'prop2', 'prop3', 'prop4']
PER_BODY_MASS: [1.745, 1.745, 1.745, 1.745, 1.745]
TOTAL:         8.725 kg
```

`assets/five_in_drone.py` sets `mass_props=sim_utils.MassPropertiesCfg(mass=1.745)`
on the spawn. That applies to **every rigid body in the articulation**, not just
the airframe — so the four propeller links each weigh a full airframe too.

`stick_to_newtons` sizes thrust for 1.745 kg. Against 8.725 kg of actual mass
that is a thrust-to-weight of **0.2**: the aircraft cannot leave the ground, and
every episode is a brick falling. Any training run since the mass change has
been learning against this.

**Fix:** set mass only on the `body` link, either by giving the props explicit
small masses in the URDF and re-importing, or by writing masses directly through
`root_physx_view.set_masses()` in a startup event — the same approach
`mdp.events.set_body_inertia` already uses for inertia, and for the same reason.

Whichever is chosen, the smoke test's total-mass check is the guard.

## 2. Inertia products are not zero

```
[FAIL] inertia products are zero    max |off-diagonal| = 4.70e-04
```

`set_body_inertia` writes the diagonal and leaves the off-diagonal terms alone,
assuming they were zero. They are not — the USD carries small products of
inertia. Against a diagonal of ~0.004 these are ~12%, which is not negligible.

**Fix:** zero the off-diagonal entries explicitly when writing the diagonal.

## 3. Inertia diagonal is right, the tolerance was too tight

```
[FAIL] PhysX inertia matches the estimate  (0.0039, 0.0055, 0.0076) vs (0.004, 0.0055, 0.0075)
```

That is float32 round-tripping through PhysX, not a real mismatch. The check
uses `< 1e-6`; it should use a relative tolerance of about 1e-3.

## 4. Some environment gets zero collective at zero action

```
[FAIL] zero action gives a plausible collective   0.000..1.071 g
```

The upper end is right. The `0.000` is not: at least one environment applies no
thrust at all on the first step. Most likely `_applied_thrust_n` is still zero
from reset when the check reads it, since it is only written in
`process_actions`. Needs confirming — if it is a reset-ordering artefact it is
harmless, and if it is not then some environment really is unpowered.

## What passed

Worth recording, because these were the uncertain ones and they hold up:

- hover points sample 0.210–0.289 across `PLANT_HOVER_RANGE`
- thrust-to-weight samples 4.29–7.98 across `PLANT_TWR_RANGE`
- the plant genuinely varies between environments (hover spread 0.079)
- the thrust curve stays convex (quad_share 0.051–0.871)
- action delays are 0–2 steps with three distinct values across envs
- the rate filter leaves real lag (alpha 0.170–0.632)
- **observation width is 1760** — v2, with action history, as the contract says
- 200 steps produce finite observations, no NaN

So the latency modelling, the plant randomisation, the thrust curve and the v2
observation all work as designed on real hardware. The failures are all in the
asset's mass and inertia, which is where the smoke test was pointed.
